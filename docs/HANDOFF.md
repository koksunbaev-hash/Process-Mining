# Передача контекста

Файл для того, кто продолжает работу — человека или ИИ. Здесь то, что дорого
далось: решения и их причины, уже найденные грабли, текущее состояние.
Прочитать целиком перед первой правкой.

---

## 1. Что это за система

Два независимых приложения в одном репозитории плюс два вспомогательных
контейнера.

```
services/qms/              Django 5 + Postgres — QMS хлебозавода:
                           заказы, производственные партии, канбан-доска,
                           этапы, качество, склад, голосовые команды
services/process-mining/   FastAPI + pm4py — аналитика:
                           карты процессов, узкие места, варианты, KPI
services/stt/              конфиг для контейнера распознавания речи (OVOS)
services/nginx/            конфиг TLS-прокси
```

QMS — источник событий. Аналитика — потребитель. Связаны HTTP-контрактом,
общей базы у них нет и быть не должно.

**Почему не одно приложение.** QMS владеет бизнес-данными и не должен падать
из-за того, что pm4py съел ядро на тяжёлом графе. Аналитика не хранит ничего,
что нельзя пересчитать, и её можно перезапускать когда угодно. Объединён
жизненный цикл (один клон, один `.env`, один `docker compose up`), а не
процессы. Это же записано в ТЗ заказчика: «Process Mining отвечает только за
приём и анализ event log».

## 3. Решения, которые не надо переделывать

**Событие имеет `event_id`, приём идемпотентен.** Дважды доставленное событие
считается дубликатом, повторный пакет с тем же `Idempotency-Key` возвращает
исходный ответ. Без этого любой ретрай задваивал бы метрики.

**События раскладываются по отдельным логам на каждый `case_type`.** Заказы,
партии и продажи — разные процессы; одна карта на всех описывала бы процесс,
которого не существует.

**Путь `/api/event-logs/import/` — вне `/api/v1`.** Контракт согласован до
появления сервиса, ломать его ради стройности URL нельзя. То же для
`/api/transcriptions/`.

**Голос только распознаёт.** Разбор команды и её выполнение — на стороне QMS,
и обязательно с подтверждением человеком. Партия сама не двигается.

**Whisper в стеке один, и он в контейнере `stt`.** Сайт и Android-приложение
приходят к нему разными дверями (`/api/transcriptions/` с callback-ом и
`/api/transcriptions/sync` соответственно), но модель одна. У backend-а
PushToTalk была своя — это давало полтора лишних гигабайта в памяти, второе
место настройки и два разных ответа на одну запись. Обратно её заводить не
надо. Цена решения записана: OVOS не принимает `initial_prompt`, поэтому
подсказка со списком кодов партий потеряна. Подробности —
[PUSHTOTALK.md](PUSHTOTALK.md).

**Ролей три, и их не надо дробить обратно.** `admin`, `manager`, `user` —
настраивает, распоряжается, работает. Раньше их было шестнадцать по названиям
должностей цеха, и каждая проверка прав перечисляла, кто из шестнадцати её
проходит; списки разъезжались — технолог был в `READ_ALL_ROLES`, но не в
`MANAGER_ROLES`, мастер не был нигде, кроме отчётов. Должность человека теперь
записана в имени пользователя, подразделении и группе Django, а роль отвечает
только за права. Цена решения записана: пропало разделение по этапам и роль
«только чтение», подробности — в [SESSION-2026-08-11.md](SESSION-2026-08-11.md).

**Меню и доступ описаны в одном месте** — `apps/accounts/navigation.py`. Раздел
знает свои адреса целиком, включая формы и карточки записей, и
`SectionAccessMiddleware` проверяет их на каждый запрос. Скрытый пункт, до
которого можно дойти, набрав адрес руками, — это не разграничение, а вежливая
просьба. Условия по ролям в шаблоне не писать: разметка меняется, а обещание
«сотрудник не видит заказы» — нет.

**Админка Django — только у администратора.** Она обходит любое разграничение:
`is_staff` у менеджера означает доступ к пользователям, заказам и всему
остальному мимо ролей. `seed_bakery` приводит флаги к своему списку и у уже
заведённых пользователей, потому что `get_or_create(defaults=...)` до
существующих не доходит.

**Вызовы pm4py — в `app/core/mining.py`.** Его API дрейфует между версиями,
обновление должно править один файл. Единственное исключение —
`app/core/ingestion.py:83`, где `pm4py.read_xes` читает XES: больше это делать
некому. Других импортов pm4py в коде нет, и заводить их не надо.

## 4. Что уже сделано

**Веб-консоль аналитики переписана.** Была неработоспособна: одна лишняя скобка
ломала весь `<script>`, поэтому не работали ни язык, ни загрузка, ни карта.
Сейчас: i18n через `data-i18n` (en/ru/kk), drag&drop, просмотрщик SVG с
зумом/панорамой/поиском, вкладки вариантов и узких мест, выбор сохранённого лога.

**Приём событий** `POST /api/event-logs/import/` — CSV пакетами, checksum,
идемпотентность, построчная валидация с кодами ошибок.

**Голосовые команды.** QMS пишет webm/opus → аналитика декодирует в WAV через
ffmpeg → OVOS/faster-whisper распознаёт → результат уходит обратно callback-ом
с подписью HMAC-SHA256 → QMS разбирает в намерение → человек подтверждает →
партия едет по доске. Push-to-talk: удержание кнопки или пробела.

**Канбан-доска** переделана: карточка показывает номер партии, продукт,
количество, клиента, срок; анимация переходов.

**Разграничение по ролям.** Меню собирается по роли: у администратора и
менеджера семнадцать разделов по группам, у сотрудника восемь сплошным списком
(доска, партии, голосовые сообщения, склад, рецептуры, проблемы, уведомления,
настройки). Прямые ссылки закрыты посредником, отказ уводит на свой раздел с
объяснением.

**Страница настроек** `/settings/` — личные данные и смена пароля для всех;
справочники и этапы производства для менеджера и администратора. Этап с
партиями выключить нельзя, порядок этапов меняется стрелками через свободное
значение `sequence`.

**Коннектор 1С** (`app/connectors/onec.py`) — вытягивает документы по OData и
шлёт в приём событий.

**HTTPS** — nginx с самоподписанным сертификатом.

**Монорепозиторий** — оба проекта сведены под `services/`, один compose.

## 5. Грабли, на которые уже наступили

Не наступать снова. Каждая стоила времени.

**Django `{# … #}` — комментарий только в одну строку.** Многострочный
печатается на странице. Наступал дважды. Для многострочных `{% comment %}`.

**Браузер даёт микрофон только в защищённом контексте.** `http://<ip>` не
подходит, `localhost` подходит. Отсюда HTTPS — это не про секретность, а
единственный способ включить голос на других компьютерах.

**Django отвергает незнакомый `Host` с кодом 400.** Внутренний callback идёт на
`http://qms:8000/`, поэтому `qms` обязан быть в `ALLOWED_HOSTS`. Внешний IP —
тоже.

**gunicorn по умолчанию — один синхронный воркер.** Один медленный запрос вешал
весь сайт. Сейчас 3 воркера × 4 потока в `docker-entrypoint.sh`.

**Образ распознавания:** `smartgic/ovos-stt-server-fasterwhisper`, тег только
`alpha` (не `latest`). Модель задаётся **файлом** `services/stt/mycroft.conf`, а
не переменными окружения. Имена моделей без префикса: `small`, а не
`whisper-small`. Зашитый в образ `whisper-medium` нерабочий — падает на
`assert model in MODELS`.

**Этот образ ждёт WAV с заголовком, а не сырой PCM** — иначе
`could not be read as PCM WAV`. Декодируем через ffmpeg во временный файл (в
поток нельзя: в потоковом WAV-заголовке нет длины, читатели обрезают звук).

**Речь не произносит пунктуацию.** Whisper пишет `B107`, в базе `B-107`. Точное
сравнение не сходится. Сравнивать по буквам и цифрам (`_squash` в
`voice_process_mining.py`).

**Плагин не отдаёт оценку уверенности.** Показывать «0%» и предупреждение
нельзя — каждая верная команда выглядела подозрительной.

**Обновление канбан-доски** принудительно подставляло `demo=demo` и обнуляло
доску, когда партии перестали быть демонстрационными.

**Аргументы вызова считаются до самого вызова.** `move_batch_view` вычислял
`require_comment=stage.sequence < …` перед `move_batch`, а у партии на
последнем этапе следующего этапа нет — `stage` был `None`, и кнопка «Дальше →»
на карточке в колонке «Готово» давала 500. Сама `move_batch` пустой этап
отвергает штатно; падало то, что считалось до неё. Кнопка теперь не рисуется
в последней колонке (`column.has_next`), а вид отвечает осмысленно.

**`messages.get_messages(request).used` — это не «ошибок не было».** Флаг
означает «сообщения отрендерены», а при JSON-ответе их никто не рендерит, так
что drag&drop всегда рапортовал успех, а текст ошибки всплывал позже на
посторонней странице. Признак успеха теперь возвращается явно (`{ok, error}`),
и на AJAX-пути сообщения не ставятся вовсе. В JS смотреть надо на `result.ok`,
а не на `response.ok`: отклонённый перенос — это честный HTTP 200.

**pm4py падает с KeyError**, если активность встречается только в кейсах из
одного события: узла нет, а в стартовые/конечные она попадает. Передавать
только то, что реально нарисовано.

**Правило `data/` в `.gitignore` было без якоря** — и глушило не только
рантайм-каталоги, но и Kotlin-пакет
`app/src/main/java/com/example/push_to_talk/data/`: весь сетевой слой
Android-приложения ни разу не попал в коммит, а `NetworkModule` его
импортирует. Приложение из репозитория не собиралось, и git об этом молчал —
`git status` чистый, файлов нет. Правило теперь якорное
(`/services/process-mining/data/`). Проверять новое правило так:
`git check-ignore -v <путь>`.

**Мохибейк в `services/pushtotalk/backend`** — те же грабли, что ниже про
PowerShell, но с последствием хуже комментариев: испорченный текст лежал в
`initial_prompt`, то есть подсказка модели состояла из мусора. Развернуть
обратно: `текст.encode('cp1251').decode('utf-8')` (байт `0x98` в cp1251 не
определён, его пришлось переносить руками).

**Дорожка `auto` в CSS grid не может стать уже своего min-content.** Если
внутри таблица с неразрывными колонками, дорожка раздувается до её ширины и
уносит страницу вбок. Наступали дважды: на канбан-доске и на странице настроек.
Лечится `grid-template-columns: minmax(0, 1fr)` или `min-width: 0` на элементе.

**Тестовый клиент Django ходит с хостом `testserver`.** Если его нет в
`ALLOWED_HOSTS`, все ответы приходят с кодом 400 — молча, без объяснения. При
проверках на стенде брать хост из настроек: `Client(SERVER_NAME=...)`.

**`get_or_create(defaults=...)` до существующих записей не доходит.** Правка
спецификации в команде посева ничего не меняет там, где пользователи заведены
прошлым запуском. Если правка обязана доехать — приводить поля явно.

**PowerShell 5.1 портит UTF-8.** `Get-Content`/`Set-Content` работают в ANSI —
кириллица превращается в мохибейк. Для файлов с кириллицей использовать Python
или bash, не PowerShell.

**Windows-консоль в cp1252** — при выводе кириллицы из Python нужен
`PYTHONIOENCODING=utf-8`.

## 6. Данные 1С — что выяснено

Endpoint `https://goldsapa.24c.kz/goldsapa/odata/standard.odata`, Basic-авторизация,
1С:Бухгалтерия для Казахстана. База **живая**: 106 549 документов реализации,
свежие за сегодня.

**Связей между документами нет.** `ДокументОснование` и `Сделка` пусты во всех
300 проверенных проведённых документах. Проследить путь одной сделки
невозможно — данных для этого просто нет. Восстанавливать связи по суммам и
датам нельзя: получится уверенная картинка процесса, которого не существует.

Поэтому **кейс = контрагент + месяц**. Отвечает на вопрос «как идёт работа с
клиентом и где застревает».

**Время суток недостоверно** — документы проводят пачками, у всех один и тот же
час. Работать с точностью до дня.

**Документы из будущего** — это непроведённые черновики, отсекаются фильтром
`Posted eq true`.

`СчетНаОплатуПокупателю` в этой базе не проводят вообще — цепочка начинается с
отгрузки.

Результат последней выгрузки: 12 464 документа → 1295 событий, 903 кейса.
Находка: **счёт-фактуру выписывают через 11.5 дней после отгрузки** (медиана).
Эта цифра надёжна.

**Осторожно с цифрой «43.7% только отгрузка»** — это частично артефакт нарезки
по календарным месяцам: отгрузка 30 июля и фактура 3 августа попадают в разные
кейсы. Как долю нарушений её называть нельзя.

## 7. Что НЕ сделано

- Выгрузка из 1С запускается вручную, расписания нет
- Номенклатура из 1С в справочник QMS не переносилась
- Нарезка кейсов скользящим окном вместо календарного месяца
- Точность распознавания на шуме цеха не измерена
- Postgres для аналитики (сейчас SQLite → одна реплика)
- `tenant` фильтрует, но не изолирует
- Rate limiting отсутствует
- Пароли демо-пользователей открыто лежат в публичном репозитории — сведение
  ролей их не заменяет: у кого есть пароль от `manager`, тот и входит менеджером
- Порты 8000/8001 открыты без TLS
- Роли «только чтение» нет. Аудитор и директор были единственными, кому
  запрещалась запись; после сведения ролей писать может любой вошедший.
  `is_read_only_role` всегда отвечает «нет» и оставлена как единственное место,
  куда возвращать запрет
- Партию двигает любая роль. Разделение по этапам («оператор печи двигает
  только печь») ушло вместе с должностями. Кто перевёл — по-прежнему в
  `BatchStageHistory`

### Осталось открытым после сверки кода 3 августа 2026

Проверено по исходникам, в старом списке не значилось. Что нашли тогда же и
сразу закрыли — ниже отдельным списком, чтобы не чинить дважды.

**Событие может застрять в `PROCESSING` навсегда.** Статус ставится внутри
транзакции, а снимается только кодом после HTTP-вызова
(`apps/process_mining/services.py`, `export_pending_events_to_process_mining`).
Падение процесса во время запроса — и событие не подберёт ни
`choose_pending_events` (только `PENDING`), ни `retry_failed_events` (только
`FAILED`). `DEAD_LETTER` не разгребает никто.

**`Idempotency-Key` меняется на каждой попытке.** Приём умеет возвращать
исходный ответ по ключу (`app/api/integration.py`), но QMS шлёт новый
`export_id` на каждый вызов, а коннектор 1С — свежий `uuid4` (`onec.py`).
Реально от задвоения спасает только дедуп по `event_id`; заявленный в разделе 3
повтор пакета не работает.

**Ключ кеша на `POST /api/v1/mine` не включает содержимое файла**
(`app/services/mining_service.py`). Для `discover` это закрыто
`use_cache=False`, а `statistics`/`variants`/`bottlenecks` такого флага не
имеют: два клиента с разными файлами и одинаковыми фильтрами получают один
ключ, и второй 900 секунд видит чужую аналитику.

**Загрузка лога блокирует единственный процесс.** `upload_log` и
`import_events` разбирают CSV/XES и пишут в SQLite синхронно внутри `async def`,
не уходя в пул потоков. Пока `pm4py.read_xes` жуёт большой XES, сервис не
отвечает вообще ни на что. С одним воркером (см. ниже) это заметнее, чем было.

### Закрыто веткой `demo-hardening`, 3 августа 2026

- **Демо больше не попадает в событийный лог.** Событие несёт `is_demo`, экспорт
  пропускает всё, что привязано к демо-партии или демо-заказу, а `reset_demo`
  убирает свои неотправленные события — оба внешних ключа `SET_NULL`, без этого
  они бы уехали как рабочие. Фильтр сделан подзапросом по id, а не через
  `batch__is_demo`: по nullable-ключу Django строит LEFT OUTER JOIN, а
  PostgreSQL не даёт `SELECT … FOR UPDATE` по внешней стороне такого соединения.
  На SQLite `FOR UPDATE` игнорируется, поэтому в тестах это не видно.
- **Дашборд считает цех, а не демо.** Раньше фильтр `is_demo` был только в
  `filter_batches`.
- **Аналитика запущена в один процесс.** Было `uvicorn --workers 2` при том, что
  реестр заданий и кеш живут в памяти воркера: `discover/async` отдавал `job_id`
  из одного процесса, а `GET /jobs/{id}` попадал в другой и отвечал 404.
- **Заказ готов, когда готовы все его партии,** а не первая из них.
- **Доска не падает на последней колонке** и честно показывает отказ переноса.
- **На чистом клоне поднимается прокси** — шаг с `make-cert.sh` теперь в README.

## 8. Команды

Развернуть изменения:

```bash
cd ~/Process-Mining && git pull && docker compose up -d --build <сервис>
```

Выгрузка из 1С:

```bash
docker compose exec process-mining python -m app.connectors.onec --days 60
```

Тесты аналитики (37 штук):

```bash
cd services/process-mining && pytest -q
```

Наполнить QMS данными для демонстрации:

```bash
docker compose exec qms python manage.py seed_bakery
docker compose exec qms python manage.py create_kanban_demo --count 13 --user admin
```

Откат к рабочему состоянию демо: метка `demo-working`.

**После правки статики QMS обязательно `Ctrl+F5`** — иначе браузер отдаст
старый JS из кеша, и правка будет выглядеть неработающей.
