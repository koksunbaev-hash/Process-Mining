# Как QMS передаёт данные в цифровой двойник и Grafana

Что видно в 3D-сцене на табло каждой машины — «Продукт», «Заказ», «Карточка»,
«Этап» — приходит туда из QMS. Ниже вся цепочка: кто, куда и когда пишет, как
включить, как проверить и что делать, когда данные не доходят.

## Цепочка целиком

```
QMS (канбан-доска)
   │  партию перетащили на машину / перевели / удалили
   ▼
apps/bakery/twins.py         сигналы Django, после коммита, в фоновом потоке
   │  HTTP PUT, basic-авторизация
   ▼
Eclipse Ditto (OpenTwins)    http://192.168.0.136:30525
   │  things/<thingId>/features/product/properties
   ▼
Grafana + 3D-сцена           http://192.168.0.136:30718  (сервис openegiz-grafana, NodePort)
```

Телеметрия счётчиков (ток, напряжение, киловатт-часы) идёт другим путём — от
самих устройств через MQTT в InfluxDB — и с QMS никак не связана. QMS отвечает
только за производственную часть: что за продукт сейчас на машине, какая
партия, какой заказ, на каком этапе.

В двойнике это две разные фичи, и они не пересекаются:

| фича | кто пишет | что внутри |
|---|---|---|
| `measurements` | счётчик через MQTT | ток, напряжение, мощность, энергия |
| `product` | **QMS** | продукт, количество, карточка, заказ, клиент, статус, этап, время |

## Что именно отправляет QMS

Одним PUT на машину — плоский набор свойств, без вложенности (интерфейс
OpenTwins печатает каждое свойство отдельной строкой):

```json
{
  "product": "Багет Луковый",
  "quantity": "27 шт",
  "card": "03",
  "order": "№0369",
  "customer": "Производство",
  "status": "в работе",
  "stage": "Печь",
  "started_at": "17.08.2026 16:10",
  "updated_at": "19.08.2026 15:24"
}
```

Свободная машина отправляет тот же набор ключей с прочерками и
`"status": "свободно"` — форма карточки не должна меняться от того, занята печь
или нет.

## Связь машины с двойником

Единственное, что связывает две системы, — поле `twin_id` у устройства в QMS.
В нём лежит полный `thingId` из Ditto:

| машина в QMS | twin_id |
|---|---|
| Печь 2 | `digitalegiz:ESP32_Dala_Meter_001994` |
| Миксер 1 | `digitalegiz:ESP32_Dala_Meter_001990` |

Заполняется в админке: **Администрирование → Производственные устройства →
поле «цифровой двойник (thingId)»**. Пустое поле означает «у машины двойника
нет» — такие устройства модуль молча пропускает, ошибки не будет.

Узнать `thingId` можно в самом Ditto:

```bash
curl -u ditto:ditto http://192.168.0.136:30525/api/2/search/things | jq '.items[].thingId'
```

## Включение

Интеграция **выключена по умолчанию** (`DITTO_ENABLED` = False). Это главная
причина, по которой данные «перестают обновляться»: код на месте, настройки в
`.env` есть, а флага нет.

В `~/Process-Mining/.env`:

```
DITTO_ENABLED=True
DITTO_BASE_URL=http://192.168.0.136:30525
DITTO_USERNAME=ditto
DITTO_PASSWORD=ditto
DITTO_TIMEOUT_SECONDS=5
```

После правки перезапустить QMS:

```bash
cd ~/Process-Mining && docker compose up -d qms
```

## Когда QMS отправляет данные

Автоматически — при любом движении партии: перевод по этапам, назначение на
машину, снятие с неё, удаление партии. Отправка идёт **после коммита
транзакции, в фоновом потоке**: доска не ждёт ответа Ditto, оператор не стоит у
перетащенной карточки.

Уходя с машины, партия обновляет **две** машины — прежнюю и новую, иначе
покинутая печь показывала бы вчерашний хлеб.

Доставка намеренно негарантированная: Ditto здесь витрина, а не источник
истины. Сеть моргнула — в лог уйдёт предупреждение, партия переедет как ни в
чём не бывало, а двойник отстанет на одно обновление.

## Ручная синхронизация

Догнать отставшую витрину — перелить состояние всех машин целиком:

```bash
cd ~/Process-Mining && docker compose exec -T qms python manage.py sync_twins
```

Посмотреть, что будет отправлено, ничего не отправляя:

```bash
docker compose exec -T qms python manage.py sync_twins --dry-run
```

Запускать после включения интеграции, после простоя Ditto или когда витрине
просто не верится.

## Проверка

**Что реально лежит в двойнике:**

```bash
curl -s -u ditto:ditto \
  http://192.168.0.136:30525/api/2/things/digitalegiz:ESP32_Dala_Meter_001994/features/product
```

Ответ должен содержать свежее `updated_at`.

**Что говорит QMS:**

```bash
docker compose exec -T qms python manage.py sync_twins --dry-run | head -5
```

**В самой сцене** — обновить страницу Grafana и посмотреть на табло машины.

## Если данные не доходят

| симптом | причина | что делать |
|---|---|---|
| На табло «Данные не обновлялись с …» | интеграция выключена или QMS давно не двигал партии | проверить `DITTO_ENABLED`, прогнать `sync_twins` |
| `sync_twins` пишет «Интеграция выключена» | нет `DITTO_ENABLED=True` в `.env` | добавить флаг, перезапустить `qms` |
| «Нет устройств с заполненным twin_id» | у машин пустое поле связи | заполнить `twin_id` в админке |
| В логе `Ditto: не удалось обновить …` | Ditto недоступен, сменился адрес или пароль | проверить `DITTO_BASE_URL`, доступность порта 30525 |
| Данные меняются только после `sync_twins` | флага нет, работает только ручной запуск | включить `DITTO_ENABLED` |

Логи QMS:

```bash
docker compose logs --tail=50 qms | grep -i ditto
```

## Что где лежит в коде

| файл | назначение |
|---|---|
| `services/qms/apps/bakery/twins.py` | payload, транспорт, сигналы |
| `services/qms/apps/bakery/management/commands/sync_twins.py` | ручная переливка |
| `services/qms/apps/bakery/models.py` | поле `ProductionUnit.twin_id` |
| `services/qms/config/settings.py` | настройки `DITTO_*` |
| `services/qms/apps/bakery/tests/test_twins.py` | тесты |

## Добавить новую машину в связку

1. Завести устройство в Ditto (или найти существующее) и узнать его `thingId`.
2. В админке QMS открыть машину и вписать `thingId` в поле «цифровой двойник».
3. Прогнать `sync_twins` — состояние уедет сразу, не дожидаясь движения партий.
4. Проверить `curl`-ом, что фича `product` появилась.
