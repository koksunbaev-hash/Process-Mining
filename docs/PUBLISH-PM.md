# Опубликовать аналитику на pm.kzt.asia

Заявка администратору VPS. Консоль Process Mining уже работает и доступна через
туннель — не хватает только записи в DNS и блока в Caddy. Оба изменения на
`185.197.249.105`, со стороны виртуалки править нечего.

Схема та же, что у `qms.kzt.asia`, отличается только порт.

---

## Что уже готово

Проверено с виртуалки в день составления заявки:

| Проверка | Результат |
|---|---|
| Контейнер `process-mining` | `Up (healthy)` |
| Туннель WireGuard | `wg0` = `10.66.66.32` |
| `https://10.66.66.32:8443/` | `200` — сюда и проксировать |
| Сертификат nginx на виртуалке | самоподписанный |
| Проверка заголовка `Host` | отсутствует |

Последняя строка — почему на виртуалке ничего не меняется. У QMS иначе: Django
отвергает незнакомый `Host` кодом 400, поэтому домен приходится вписывать в
`ALLOWED_HOSTS`. Аналитика отвечает `200` на запрос с любым `Host`, и добавлять
имя ей некуда.

---

## Шаг 1. DNS

```
pm.kzt.asia.    A    185.197.249.105
```

Проверить, что разошлось (обычно минуты, изредка до часа):

```bash
dig +short pm.kzt.asia
```

Должен ответить адресом VPS.

---

## Шаг 2. Caddy на 185.197.249.105

В `/etc/caddy/Caddyfile`:

```
pm.kzt.asia {
    reverse_proxy https://10.66.66.32:8443 {
        transport http {
            tls
            tls_insecure_skip_verify
        }
    }
}
```

`tls_insecure_skip_verify` — потому что у nginx на виртуалке самоподписанный
сертификат, а этот участок идёт внутри туннеля, где некому подделываться.
Наружный сертификат, который видит браузер, выпускает Caddy, и он настоящий.

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

---

## Шаг 3. Проверка

```bash
# страница отдаётся
curl -sS -o /dev/null -w '%{http_code}\n' https://pm.kzt.asia/

# сертификат настоящий, предупреждений в браузере нет
curl -sSI https://pm.kzt.asia/ | head -1
```

Ожидается `200`.

---

## Если 502 или 504

Caddy не достучался до `10.66.66.32:8443`. Проверить туннель со стороны VPS:

```bash
ping -c3 10.66.66.32
ip -brief addr show wg0
```

---

## Откат

Убрать блок из `Caddyfile`, затем `systemctl reload caddy` — адрес перестаёт
отвечать. На работу самой системы это не влияет: аналитика продолжает быть
доступной в локальной сети и через туннель.

---

## Чего эта заявка не отменяет

**Консоль закрыта одним значением — `PM_API_KEYS`.** Этот ключ входит в девять
секретов, уехавших 10 августа коммитом `280565e` в публичный репозиторий. Файлы
оттуда убраны, но объекты остаются доступны по идентификатору коммита.

Пока ключ не заменён, публичный адрес отдаёт аналитику — карты процессов, узкие
места, выгрузку из 1С — любому, кто читал ту историю. Локально это терпимо,
потому что снаружи туда не дойти; публикация это свойство снимает.

Замена — раздел 0.1a в [PUBLIC-DEPLOY.md](PUBLIC-DEPLOY.md). Коротко: сгенерировать
`openssl rand -hex 32`, вписать в `.env` на виртуалке, перезапустить оба
контейнера. Ключ нужен обеим сторонам сразу — иначе приём событий начнёт отдавать
403.

**Рейт-лимит будет общим на всех.** В nginx `real_ip` не покрывает
`10.66.66.0/24`, поэтому все посетители выглядят одним адресом. Для второго
публичного сервиса это заметнее, чем для первого. Лечится одной строкой
`set_real_ip_from 10.66.66.0/24;`, но правку по просьбе пока не применяли.
