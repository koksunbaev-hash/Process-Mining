# Приём event log из внешней системы

Ответ на `docs/process_mining_csv_integration.md` со стороны KMS/QMS: что именно
реализовано, с какими лимитами и как это проверить.

Реализовано по контракту версии схемы **1.0**.

---

## Endpoint

```
POST /api/event-logs/import/
```

Путь намеренно вне `/api/v1`: он часть контракта, согласованного до появления
этого сервиса. Форма без завершающего слэша тоже работает (307 с сохранением
тела и метода).

`Content-Type: multipart/form-data`.

| Поле формы | Обяз. | Смысл |
|---|---|---|
| `file` | да | CSV в UTF-8, разделитель — запятая |
| `export_id` | да | UUID пакета |
| `source` | нет | Система-источник, по умолчанию `unknown`. Например `kms_bakery` |
| `schema_version` | нет | Сейчас `1.0` |
| `checksum` | нет | SHA-256 от байтов CSV. Если передан — проверяется |
| `events_count` | нет | Число строк без заголовка. Расхождение пишется в лог, импорт не прерывает |

Заголовки:

```http
Authorization: Bearer <token>
Idempotency-Key: <export_id>
```

Вместо `Authorization: Bearer` принимается и `X-API-Key: <token>` — что удобнее.
Ключи задаются переменной `PM_API_KEYS` (несколько через запятую, разумно
выдать источнику отдельный).

---

## CSV

Колонки читаются **по имени заголовка**, а не по позиции: если вы добавите
колонку в конец, импорт не сломается. Обязательные — `event_id`, `case_id`,
`activity`, `timestamp`.

```csv
event_id,case_id,case_type,activity,timestamp,user_id,user_name,resource,product_id,product_name,batch_number,order_number,from_stage,to_stage,status,quantity,unit,problem_type,metadata
```

`timestamp` — ISO 8601 с таймзоной (`2026-07-28T14:30:12+05:00`). Внутри
приводится к UTC.

`metadata` — JSON-объект в одной ячейке; его ключи разворачиваются в атрибуты
события. Если значение не разбирается как JSON, оно сохраняется как есть в
`_raw`, строка при этом **не** отбраковывается.

Остальные колонки сохраняются как атрибуты события и доступны через
`GET /api/v1/logs/{id}/events`. Ничего не теряется.

`resource` берётся из колонки `resource`, а при её отсутствии — из `user_name`.

---

## Раскладка по логам

События **разных `case_type` попадают в разные логи**. Это не деталь
реализации, а необходимость: заказ и производственная партия живут разными
жизненными циклами, и общая карта процесса по ним описывала бы процесс,
которого не существует.

Лог создаётся автоматически при первом событии. Его идентификатор
детерминированно выводится из пары `(source, case_type)`, поэтому источнику не
нужно ни хранить `log_id`, ни создавать логи заранее — достаточно продолжать
слать пакеты.

Имя лога выглядит как `kms_bakery · production_batch`, а `log_id` возвращается
в ответе в поле `log_ids`.

---

## Идемпотентность

Две независимые защиты, обе обязательны для безопасной автоматической подкачки.

**По `event_id`.** Событие с уже известным `event_id` в этом логе считается
дубликатом и попадает в счётчик `duplicates`, а не импортируется повторно.
Гарантия закреплена частичным уникальным индексом в БД, то есть не зависит от
корректности вызывающего кода. События без `event_id` (например, из ручной
загрузки файла) под ограничение не подпадают — распознать их всё равно нечем,
а придумывать ключ по содержимому нельзя: одна и та же активность в кейсе
законно повторяется.

**По `Idempotency-Key`.** Повторный пакет с тем же ключом возвращает **тот же
самый ответ**, что и в первый раз, ничего не импортируя. Именно это делает
безопасным ретрай источника после таймаута. Если заголовок не передан, ключом
служит `export_id`.

## Ответ

```json
{
  "status": "accepted",
  "export_id": "9f1c...",
  "received": 84,
  "accepted": 84,
  "duplicates": 0,
  "rejected": 0,
  "errors": [],
  "log_ids": ["2e6d953ab7ec8f453884"]
}
```

`status` — `accepted`, если отбраковок нет, иначе `partially_accepted`.
`log_ids` — расширение контракта: логи, в которые лёг пакет, по одному на
`case_type`. Поле можно игнорировать.

По правилам KMS `accepted` и `duplicates` считаются доставленными.

### Коды ошибок строк

Отбраковка строки не влияет на остальной пакет.

| `code` | Когда |
|---|---|
| `MISSING_EVENT_ID` | пустой `event_id` |
| `MISSING_CASE_ID` | пустой `case_id` |
| `MISSING_ACTIVITY` | пустая `activity` |
| `INVALID_TIMESTAMP` | `timestamp` пуст или не разбирается |

### Ошибки уровня пакета

Возвращаются с HTTP 422 и телом `{"error": {"code": ..., "details": {"code": ...}}}`.

| `details.code` | Когда |
|---|---|
| `CHECKSUM_MISMATCH` | SHA-256 не совпал с переданным |
| `INVALID_SCHEMA` | нет обязательной колонки |
| `INVALID_ENCODING` | файл не в UTF-8 |

Ошибка 5xx или таймаут означает «повторяйте позже» — пакет не был учтён.

## Лимиты

| Параметр | Значение | Настройка |
|---|---|---|
| Размер тела запроса | 64 МБ | `PM_MAX_UPLOAD_MB` |
| Событий в логе | 2 000 000 | `PM_MAX_EVENTS_PER_LOG` |
| Кодировка | UTF-8, BOM допускается | — |
| Разделитель | запятая | — |
| Rate limit | нет | — |

Рекомендуемый размер пакета — 100–1000 строк, как в `PROCESS_MINING_BATCH_SIZE`.

Health-эндпоинт для мониторинга: `GET /health/ready` (без авторизации).
Swagger: `/docs`, OpenAPI: `/openapi.json`.

## Проверка

```bash
CSV=events.csv
CHK=$(sha256sum "$CSV" | cut -d' ' -f1)

curl -X POST http://<host>:8000/api/event-logs/import/ \
  -H "X-API-Key: <token>" \
  -H "Idempotency-Key: $(uuidgen)" \
  -F "file=@$CSV" \
  -F "export_id=$(uuidgen)" \
  -F "source=kms_bakery" \
  -F "schema_version=1.0" \
  -F "checksum=$CHK" \
  -F "events_count=$(( $(wc -l < "$CSV") - 1 ))"
```

Импортированный лог сразу доступен для анализа — и в веб-консоли на `/`
(выпадающий список «Источник»), и через API:

```
GET  /api/v1/logs/{log_id}/statistics
GET  /api/v1/logs/{log_id}/bottlenecks
GET  /api/v1/logs/{log_id}/variants
GET  /api/v1/logs/{log_id}/map?algorithm=dfg_performance&format=svg
```

## Что осталось за рамками

**Голосовой контур** (`POST /api/transcriptions/` и HMAC-callback из
`docs/process_mining_integration_requirements.md`) не реализован. Модуль
распознавания в сервисе есть, но выключен флагом `PM_VOICE_ENABLED`: Whisper
требует гигабайты RAM и разворачивается отдельно.

**Push отдельными событиями** — альтернатива пакетному CSV, если понадобится
меньшая задержка: `POST /api/v1/logs/{log_id}/events` принимает JSON-массив,
поле `event_id` в каждом событии даёт ту же защиту от дублей.
