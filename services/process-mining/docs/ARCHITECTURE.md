## Ключевые решения

**Канонический формат — единственный контракт внутри.** Голос, CSV и XES сходятся в одну
и ту же таблицу из шести колонок. Любая аналитика читает только её, поэтому новый источник
данных = новая функция парсинга, и ни строчки изменений в остальном коде.

**pm4py заперт в `core/mining.py`** — за одним исключением: `core/ingestion.py` вызывает
`pm4py.read_xes`, потому что читать XES умеет только сам pm4py. Публичный API pm4py меняется
между минорными версиями, а внутренности визуализаторов переезжают ещё чаще (в прототипе это
уже выстрелило `ImportError`). Обновление библиотеки — правка этих двух файлов; других
импортов pm4py в коде нет.

**Граф отдаётся отдельно от картинки.** SVG нельзя кликнуть, отфильтровать или
анимировать. JSON-граф с частотами и длительностями можно отдать в любой фронтенд-движок.
Картинка остаётся для отчётов.

**CPU-bound работа — в пуле потоков.** pm4py и graphviz блокируют. На event loop они
положили бы весь сервис, поэтому каждый тяжёлый вызов идёт через `JobManager`.

**Кеш по содержимому.** Ключ = `log_id : blake2b(updated_at + параметры)`. Дописали
события — `updated_at` изменился — кеш инвалидировался сам. Гонок нет.

**Хранилище за интерфейсом.** `LogRepository` — три метода. Сегодня SQLite, завтра
Postgres или S3-parquet: API-слой не заметит.

**Голос — плагин, а не ядро.** Whisper требует гигабайты RAM и не нужен 90% потребителей.
Он живёт за флагом и импортируется лениво, поэтому сервис стартует меньше чем за секунду.

## Как масштабировать

| Нагрузка | Что делать |
|---|---|
| до ~1 млн событий, один сервер | как есть: SQLite + несколько воркеров uvicorn |
| несколько реплик | Postgres вместо SQLite (меняется URL в `storage/sqlite.py`), Redis для кеша |
| тяжёлые расчёты | Celery/RQ вместо `JobManager`; контракт `/jobs/{id}` не меняется |
| десятки миллионов событий | предварительная агрегация в DuckDB/ClickHouse, дискавери по сэмплу |

## Что бы я добавил следующим

1. **Rate limiting** по API-ключу (сейчас есть только лимит размера тела).
2. **Метрики Prometheus** на `/metrics`: латентность дискавери, hit rate кеша, длина очереди.
3. **Сравнение периодов**: два фильтра → дельта по узким местам. Это то, что реально
   показывают руководству.
4. **Прогноз времени завершения кейса** по префиксу маршрута (обычный градиентный бустинг
   поверх тех же признаков).
5. **Вебхуки**: «время цикла выросло на 20% за сутки» → POST в ваш сервис.
6. **Мультиарендность по-настоящему**: сейчас `tenant` — фильтр, стоит сделать его
   обязательным измерением с изоляцией на уровне ключа.
