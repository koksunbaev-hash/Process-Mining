# demo-feed

Поток событий для показа консоли процесс-майнинга, когда в КМС никто не работает.

Реальный журнал наполняется только из настоящей работы. Если на стенде её нет,
карта процесса замирает на дате последнего события — а показывать систему
партнёрам надо в произвольный день. Этот сервис поддерживает **отдельный**
журнал, который выглядит как непрерывно работающий цех.

---

Это половина пары. Вторая — [docs/KANBAN-AUTOPILOT.md](../../docs/KANBAN-AUTOPILOT.md),
которая ведёт демо-партии по канбан-доске. Они намеренно не связаны: демо с
доски в аналитику не пускают, потому что партию с доски удалить можно, а кейс
из журнала аналитики — уже нет.

## Чего он не делает

**Не трогает КМС.** Ни базы, ни outbox, ни `ProcessEvent`. Разговаривает с
аналитикой по тому же публичному контракту `POST /api/event-logs/import/`, что
и любой внешний источник — [EVENT-LOG-INTAKE.md](../process-mining/docs/EVENT-LOG-INTAKE.md).

**Не может попасть в реальный журнал.** `log_id` выводится детерминированно из
пары `(source, case_type)`, а `source` здесь свой — на стенде `bakery_line`.
Имя нейтральное, поэтому генератор сверяет его с настоящим источником
(`DEMO_FEED_REAL_SOURCE`, в compose — из `PROCESS_MINING_SOURCE`) и при
совпадении отказывается работать: иначе демо легло бы в настоящий журнал.
Это не соглашение, а свойство интейка: чтобы записать в `kms_bakery · batch`,
пришлось бы представиться именно `kms_bakery`.

**Ничего не выдумывает.** Маршруты, паузы между этапами, ресурсы, продукты,
объёмы и ритм недели взяты из `profile.json`, снятого с настоящего журнала этой
же установки.

**Не работает по выходным.** В профиле суббот и воскресений нет вовсе — цех по
ним не работает, и генератор в эти дни молчит.

## Как выключить

Три способа, от самого быстрого к самому полному.

**Пауза на ходу, без перезапуска.** Такт видит файл и ничего не делает:

```bash
docker compose exec demo-feed touch /srv/demo-feed/PAUSED
```

Снять — `rm` того же файла. Состояние при этом не трогается: сняли паузу, и
пропущенные дни досылаются сами.

**Остановить сервис:**

```bash
docker compose stop demo-feed
```

Или совсем не поднимать: `DEMO_FEED_ENABLED=0` в `.env` — значение по
умолчанию. Без явного `=1` контейнер стартует, пишет в лог, что выключен, и
простаивает.

**Убрать все сгенерированные данные.** Журнал удаляется целиком, реальные два
не затрагиваются:

```bash
curl -X DELETE "http://127.0.0.1:8001/api/v1/logs/<log_id>" -H "X-API-Key: $PM_API_KEYS"
```

`log_id` печатается в логе контейнера при первой отправке.

## Как устроен такт

Раз в `DEMO_FEED_INTERVAL_SECONDS` (по умолчанию полчаса):

1. Смотрит, какие рабочие дни с `DEMO_FEED_START_DATE` ещё не заводились.
2. Для каждого такого дня решает, сколько партий завести — треугольное
   распределение между наблюдавшимися минимумом и максимумом для этого дня
   недели. В реальных данных разброс от 7 до 40 за сутки, ровное число выдало
   бы генератор сразу.
3. Каждая партия получает маршрут (сэмплированием из 54 настоящих, изредка с
   мутацией), время старта по реальному распределению часов, паузы между
   этапами бутстрэпом из наблюдавшихся, ресурс по действию, продукт и объём.
4. Отправляет только те события, чьё время **уже наступило**. Остальные ждут
   в состоянии и уходят следующими тактами.

Поэтому журнал наполняется в течение дня, а не разовым сбросом в полночь: тот,
кто открыл консоль в три часа дня, видит события часовой давности.

**Пробелы затягиваются сами.** Контейнер лежал три дня — при старте досылает
пропущенное. Дыра в журнале выдаёт синтетику быстрее, чем что-либо ещё.

**Повтор не задваивает.** `event_id` считается от `(case_id, номер шага,
действие)`, интейк отбрасывает дубликаты по нему, а `Idempotency-Key` возвращает
прежний ответ на повторный пакет.

## Настройки

Все в корневом `.env`.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DEMO_FEED_ENABLED` | `0` | `1` включает генерацию |
| `DEMO_FEED_API_KEY` | — | Ключ аналитики, обычно `PM_API_KEYS` |
| `DEMO_FEED_SOURCE` | `demo_bakery` | Имя источника; оно же определяет журнал. На стенде `bakery_line` |
| `DEMO_FEED_REAL_SOURCE` | `kms_bakery` | Имя настоящего источника — под ним генератор не запустится |
| `DEMO_FEED_START_DATE` | `2026-09-11` | С какого дня заполнять |
| `DEMO_FEED_INTERVAL_SECONDS` | `1800` | Период такта |
| `DEMO_FEED_VOLUME` | `1.0` | Множитель объёма: `0.5` — вдвое меньше партий |
| `DEMO_FEED_MAX_BACKFILL_DAYS` | `400` | Предел разового догона |
| `DEMO_FEED_DRY_RUN` | `0` | `1` — считать, но не отправлять |

## Проверка

Совпадать с оригиналом генератор должен **близко, но не дословно**. Точное
совпадение означало бы, что копируются сами наблюдения, а это видно в консоли
с первого взгляда: карта процесса и есть инструмент поиска повторов.

```bash
DEMO_FEED_API_KEY=$PM_API_KEYS python selfcheck.py <real_log_id> <demo_log_id>
```

Скрипт ругается и на слишком большое расхождение, и на слишком точное.

Замер на трёх месяцах сгенерированных данных против настоящего журнала:

| | реальный | демо |
|---|---|---|
| действий | 10 | 10 |
| ресурсов | 14 | 14 |
| медиана прохождения | 1.67 ч | 1.72 ч |
| p90 | 3.81 ч | 3.84 ч |
| максимум | 44.9 ч | 46.5 ч |

Доли событий по всем десяти действиям сошлись в пределах 0.4 процентного пункта.
Маршрутов у демо больше (90 против 54) — за три месяца их и должно стать больше,
чем за две недели; замороженный набор как раз и выдавал бы генератор.

## Пересъём профиля

Если процесс в цеху поменяется, демо начнёт расходиться с реальностью. Тогда:
выгрузить события настоящего журнала в `raw_<log_id>.json`, поправить в
`build_profile.py` идентификаторы логов и запустить его — он перезапишет
`profile.json`. Раз в квартал достаточно.
