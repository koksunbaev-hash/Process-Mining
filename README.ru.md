# Process Mining Service

HTTP-API поверх [pm4py](https://pm4py.fit.fraunhofer.de/). Отдаёте журнал событий —
получаете карту процесса, метрики, частые маршруты, узкие места и оценку соответствия.

*[English version](README.md)*

Process mining отвечает на три вопроса о бизнес-процессе: как он идёт **на самом деле**
(а не как нарисовано в регламенте), где реальность расходится с задуманной моделью и куда
уходит время. Сервис делает всё это по HTTP, чтобы любое количество ваших проектов могло
этим пользоваться, не таща pm4py к себе внутрь.

Каждая модель возвращается **дважды**: готовой картинкой SVG/PNG для отчётов и JSON-графом
(узлы + рёбра + метрики), который можно нарисовать самому в D3, Cytoscape или React Flow.

---

## Быстрый старт

```bash
cp .env.example .env          # задайте PM_API_KEYS
docker compose up -d --build
```

Дальше <http://localhost:8000/> — веб-консоль, <http://localhost:8000/docs> — OpenAPI.

Без Docker нужен бинарь `graphviz` в PATH (`apt install graphviz`, `brew install graphviz`,
`choco install graphviz`), затем:

```bash
python -m venv .venv && .venv\Scripts\activate   # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
uvicorn app.main:app --reload --port 8000
```

Один вызов, чтобы убедиться, что всё работает:

```bash
curl -X POST http://localhost:8000/api/v1/mine \
  -H "X-API-Key: dev-key-change-me" \
  -F "file=@examples/sample_log.csv" \
  -F "algorithm=dfg_performance" \
  -F "format=svg" | jq -r '.result.image' > map.svg
```

Или полный смоук-тест: загрузка → статистика → узкие места → картинка → удаление.

```bash
python clients/python/pm_client.py --api-key dev-key-change-me
```

## Формат входных данных

Обязательны три колонки: **идентификатор кейса**, **активность**, **время**. Остальное
опционально. Названия колонок определяются автоматически (`batch_id`, `order`, `ticket` →
кейс; `step`, `action`, `task` → активность и т.д.), но догадку можно и переопределить явно.

```csv
batch_id,step,event_time,operator
B-0001,start_mixing,2026-06-01 07:00:00,Данияр
B-0001,add_ingredients,2026-06-01 07:07:00,Данияр
```

Принимается: CSV, TSV, XES (обычный или `.gz`), JSON, JSONL.

## Два способа использования

**Stateless** — один запрос, полный ответ, ничего не сохраняется. Большинству потребителей
нужен именно он.

```
POST /api/v1/mine        multipart: файл + параметры
```

**Stateful** — лог живёт на сервере, события дописываются по мере появления. Это нужно,
когда данные идут потоком: ERP, IoT, производственная линия, голосовой ввод.

| Эндпоинт | Назначение |
|---|---|
| `POST /api/v1/logs` | создать лог из JSON-списка событий |
| `POST /api/v1/logs/upload` | создать лог из файла |
| `POST /api/v1/logs/{id}/events` | дописать события |
| `POST /api/v1/logs/{id}/discover` | построить модель |
| `POST /api/v1/logs/{id}/discover/async` | то же, но сразу возвращает `job_id` |
| `GET /api/v1/logs/{id}/statistics` | время цикла, статистика по активностям и ресурсам |
| `GET /api/v1/logs/{id}/variants` | самые частые сквозные маршруты |
| `GET /api/v1/logs/{id}/bottlenecks` | куда реально уходит время |
| `POST /api/v1/logs/{id}/conformance` | fitness / precision относительно модели |
| `GET /api/v1/logs/{id}/map` | сама картинка, вставляется прямо в `<img src=...>` |

**Автоматический приём** — система-источник сама шлёт свои бизнес-события пакетами, и
никто ничего не загружает руками.

```
POST /api/event-logs/import/     multipart CSV + export_id + checksum
```

Доставка идемпотентна двумя независимыми способами: событие с уже известным `event_id`
считается дубликатом, а не импортируется заново, а повторный пакет с тем же
`Idempotency-Key` возвращает исходный ответ. Именно это делает безопасным ретрай после
таймаута. События раскладываются по отдельным логам на каждый `case_type`, потому что
заказы и производственные партии — разные процессы, и общая карта описывала бы процесс,
которого не существует. Контракт и лимиты: [docs/EVENT-LOG-INTAKE.md](docs/EVENT-LOG-INTAKE.md).

Авторизация — `X-API-Key: <ключ>` или `Authorization: Bearer <ключ>`. Пустой `PM_API_KEYS`
выключает проверку: только для локальной разработки.

Полный справочник: [docs/API.md](docs/API.md).

## Алгоритмы

| `algorithm` | Что получится |
|---|---|
| `dfg_frequency` | граф переходов, толщина рёбер по количеству |
| `dfg_performance` | граф переходов, толщина рёбер по времени ожидания |
| `petri_net_inductive` | сеть Петри, inductive miner (корректна по построению) |
| `petri_net_heuristics` | сеть Петри, heuristics miner (терпим к шуму) |
| `process_tree` | дерево процесса |
| `bpmn` | BPMN-диаграмма |

Начинайте с `dfg_performance` — именно он показывает, где теряются часы.

За читаемость отвечают две ручки. `noise_threshold` (0–1) отбрасывает редкое поведение в
inductive и heuristics. `filters.variant_coverage: 0.8` оставляет варианты, покрывающие 80%
кейсов, — самый дешёвый способ превратить «спагетти» в понятную схему.

## Что приходит в ответе

```jsonc
{
  "result": {
    "algorithm": "dfg_performance",
    "graph": { "nodes": [...], "edges": [...] },   // рисуйте сами
    "image": "<svg .../>",                          // или берите готовое
    "computed_in_ms": 327
  },
  "statistics": { "events": 497, "cases": 60, "throughput_seconds": { "median": 8520 } },
  "bottlenecks": { "bottlenecks": [...], "rework": [...] },
  "variants":    { "items": [...] },
  "warnings": [], "detected_columns": { "case_id": "batch_id" }
}
```

Узкие места ранжируются по **суммарному** съеденному времени (`среднее × количество`), а не
по среднему. Сортировка по среднему выносит наверх единичные аномалии; сортировка по сумме
показывает, что действительно стоит компании часов.

## Веб-консоль

Сервис отдаёт готовый интерфейс на `/`: загрузили лог, выбрали алгоритм, получили карту и
вкладки с вариантами, узкими местами и активностями. Языки интерфейса: английский, русский,
казахский. Светлая и тёмная темы.

Это обычная статическая страница (`app/static/`), которая ходит в тот же публичный API —
без сборки и без npm. Если пишете свой фронтенд, `app/static/app.js` можно читать как
референсный клиент.

## Профили активностей

Свободный текст названий приводится к единому виду через YAML-профили, поэтому «замес»,
«месим тесто» и `start_mixing` схлопываются в одну активность. Правила проверяются сверху
вниз, побеждает первое совпадение: `exact` → `patterns` (регулярки) → `keywords` (подстроки).

```yaml
profiles:
  bakery:
    fallback: other_activity
    passthrough: false        # true = неопознанный текст остаётся как есть
    rules:
      - activity: start_mixing
        exact: ["start_mixing"]
        keywords: ["замес", "меси"]
```

`config/activities.yaml` перечитывается автоматически при изменении файла; принудительно —
`POST /api/v1/mapping-profiles/reload`.

## Конфигурация

Переменные окружения с префиксом `PM_`. Полный список — в `.env.example`.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PM_API_KEYS` | *пусто* | Ключи через запятую. Пусто = авторизация выключена |
| `PM_CORS_ORIGINS` | `*` | В проде укажите свои домены |
| `PM_STORAGE_BACKEND` | `sqlite` | `sqlite` или `memory` |
| `PM_SQLITE_PATH` | `./data/pm.db` | Файл базы |
| `PM_MAX_UPLOAD_MB` | `64` | Лимит размера файла |
| `PM_MAX_EVENTS_PER_LOG` | `2000000` | Защита от случайного гигабайта |
| `PM_MAPPING_CONFIG` | `./config/activities.yaml` | Профили активностей |
| `PM_MAX_CONCURRENT_JOBS` | `4` | Размер пула потоков под pm4py |
| `PM_RENDER_TIMEOUT_SECONDS` | `60` | Таймаут graphviz |
| `PM_VOICE_ENABLED` | `false` | Включает эндпоинты Whisper |
| `PM_LOG_JSON` | `true` | JSON-логи, удобно для Loki / ELK |

## Структура

```
app/
├── main.py         точка сборки: всё связывается здесь и только здесь
├── config.py       настройки PM_*; больше никто не читает os.environ
├── deps.py         зависимости FastAPI: API-ключ, доступ к сервисам
├── api/v1/         HTTP-слой. Тонкий: провалидировать → вызвать сервис → отдать
├── schemas/        контракты Pydantic; правите здесь — меняется и OpenAPI
├── services/       сценарии использования, про HTTP ничего не знают
├── core/           чистая предметная логика, ни FastAPI, ни БД
│   ├── ingestion.py   CSV/XES/JSON → канонический формат, автоопределение колонок
│   ├── mining.py      единственный модуль, который импортирует pm4py
│   ├── metrics.py     KPI, варианты, узкие места, переделки (чистый pandas)
│   ├── rendering.py   graphviz → SVG/PNG/DOT, в песочнице и с таймаутом
│   └── cache.py       LRU + TTL по отпечатку входных данных
├── storage/        интерфейс репозитория + бэкенды memory и sqlite
└── jobs/manager.py пул потоков: блокирующий pm4py не трогает event loop
```

Зависимости идут только внутрь: `api` → `services` → `core`. `core` не знает ни о ком,
поэтому логику можно вызвать из CLI, воркера или теста, не поднимая HTTP.

Два решения, о которых стоит знать. **Все вызовы pm4py живут в `core/mining.py`** — его
публичный API дрейфует между минорными версиями, поэтому обновление библиотеки правится в
одном файле. **Рендер идёт в приватный временный каталог** с таймаутом: рендер в каталог
проекта — это ровно тот путь, которым получают `PermissionError` на Windows и намертво
занятый воркер на патологическом графе.

Подробнее — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Развёртывание

Штатный сценарий — `docker compose up -d --build` на виртуалке: внешних зависимостей нет,
SQLite в именованном томе, `restart: unless-stopped`, healthcheck встроен.

Перед продом: задайте настоящие `PM_API_KEYS`, замените `PM_CORS_ORIGINS=*` на свои домены,
поставьте `PM_DEBUG=false` и терминируйте TLS впереди — рабочий конфиг обратного прокси с
нужными длинными таймаутами лежит в [deploy/nginx.conf](deploy/nginx.conf).

Образ весит ~1 ГБ (pm4py тянет scipy и matplotlib). Для машины без интернета
`docker save | gzip` даёт ~400 МБ для переноса файлом.

## Ограничения

Этот раздел стоит прочитать до того, как строить на сервисе что-то своё.

- **Дедупликация работает только при наличии `event_id`.** Событие с идентификатором
  невозможно сохранить дважды; событие без него (обычная загрузка файла) добавляется
  всегда — честно отличить повторную доставку от законного повтора той же активности в
  том же кейсе нечем.
- **SQLite означает один узел.** Интерфейс `LogRepository` готов под Postgres, но
  реализации нет. Не запускайте несколько реплик на один файл БД — учтите, что в
  `deploy/k8s.yaml` стоит `replicas: 2`, это надо исправить перед использованием.
- **`tenant` — это фильтр, а не изоляция.** Он ограничивает выборку, но не запрещает
  ключу A прочитать данные арендатора B.
- **Нет rate limiting.** Есть только ограничение размера тела запроса.
- **Дискавери упирается в CPU и по умолчанию синхронный.** Большие логи стоит гонять через
  `/discover/async` + `/jobs/{id}`, а не держать HTTP-соединение открытым.
- **Голосовой ввод требует Whisper** (`PM_VOICE_ENABLED=true`, `pip install '.[voice]'`), а
  ему нужны гигабайты RAM. Именно поэтому он выключен и импортируется лениво.
